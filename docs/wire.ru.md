# Формат pkt-voidnet на проводе, версия 1 (черновик 0.1)

[English](wire.md) · **Русский**

Этот файл единственный источник истины о байтах на проводе. По этой странице и векторам из `vectors/wire-v1.txt` можно написать клиент, бота или инструмент; другого нормативного источника нет. Если код на Rust и этот файл расходятся, прав файл, а код содержит ошибку.

Статус: **черновик**. Раскладки в разделах 1-4 зафиксированы для этапа 1 и покрыты векторами. Разделы 5-6 (выводимые значения, правила рукопожатия) предварительные до этапа 2.

## 0. Соглашения

- Все целые фиксированной ширины **little-endian**. `u8`, `u16`, `u32`, `u64` беззнаковые.
- `varint` это беззнаковый LEB128, ограниченный `u32`: 1-5 байт, по 7 бит значения в байте, старший бит значит «есть ещё». **Только каноничная запись**: многобайтовый varint с последним байтом `0x00` недопустим, как и любое значение выше `u32::MAX`.
- Датаграмма не длиннее **1400 байт** (`MAX_DATAGRAM`). Более длинный ввод отбрасывается.
- **Строгий разбор.** Любое нарушение этого файла (зарезервированное значение, неверная длина, ненулевое дополнение, неизвестный тег, неканоничный varint, порядок кадров) заставляет получателя **молча отбросить всю датаграмму**. Ответа об ошибке на неразобранную датаграмму не посылают никогда.
- У каждой раскладки ровно одна допустимая запись. Разбор допустимой датаграммы и кодирование результата возвращают те же байты (это проверяет цель фаззинга).

## 1. Виды датаграмм

Первый байт задаёт вид. Всё, чего нет в таблице, недопустимо.

| Байт | Вид | Направление | Длина |
|---|---|---|---|
| `0x00` | DATA | в обе стороны | 12-1400 |
| `0x80` | HELLO | клиент серверу | ровно 64 |
| `0x81` | CHALLENGE | сервер клиенту | ровно 13 |
| `0x82` | RESPONSE | клиент серверу | ровно 64 |
| `0x83` | ACCEPT | сервер клиенту | 22 + `blob_len` |
| `0x84` | REJECT | сервер клиенту | ровно 10 |
| `0x01` | зарезервировано: запечатанная DATA (необязательный слой шифрования) | | в v1 недопустимо |

Правило дизайна: **ответ непроверенному адресу никогда не длиннее датаграммы, которая его вызвала.** HELLO (64 байта) может вызвать только CHALLENGE (13) или REJECT (10); RESPONSE (64) только ACCEPT (не более 54) или REJECT (10).

## 2. DATA

```
00 | token:u64 | pn:u16 | frame...
```

- `token`: токен сессии, выданный в ACCEPT, одинаковый в обе стороны одного соединения. Сравнивается за постоянное время.
- `pn`: младшие 16 бит **номера пакета** отправителя. Номера пакетов 64-битные, начинаются с 0 в каждом направлении, растут на 1 с каждой отправленной DATA и **никогда не повторяются: повторная отправка получает новый номер**. Получатель восстанавливает полное значение (раздел 2.1).
- Нужен хотя бы один кадр. Кадры занимают остаток датаграммы без остатка.

### 2.1 Восстановление номера пакета

Пусть `expected` это наибольший принятый полный номер пакета плюс 1 (0, если ничего не принято). Полный номер это единственное значение, сравнимое с `pn` по модулю 2^16, в интервале `(expected - 2^15, expected + 2^15]`. Если оно получилось бы отрицательным, датаграмма отбрасывается. Это верно, пока настоящий номер лежит в этом интервале; отправитель не должен уходить вперёд от наибольшего принятого получателем номера на 2^15 и более.

### 2.2 Окно приёма

Получатель хранит окно из **256** последних номеров пакетов. Номер внутри окна, уже принятый, это **дубликат**, номер ниже окна это **слишком старый**; оба отбрасываются до любой другой обработки. Именно это гарантирует, что датаграмма не будет доставлена дважды.

### 2.3 Кадры

Кадр начинается с однобайтового **тега**.

| Тег | Кадр |
|---|---|
| `0x00`-`0x0F` | MSG: сообщение приложения в канале `tag` |
| `0x10` | ACK |
| `0x11` | PING |
| `0x12` | DISCONNECT |
| `0x13`-`0x1F` | зарезервировано (фрагмент, квитанция, кредит); в v1 недопустимо |
| `0x20`-`0xFF` | недопустимо |

Правила порядка: **ACK, если есть, первый кадр; DISCONNECT, если есть, последний; ACK, PING и DISCONNECT встречаются не более одного раза.** Датаграмма только с кадром ACK называется *ack-only*; любая другая *требует подтверждения* и обязывает получателя её подтвердить.

#### MSG

```
tag(= канал) | [mseq:u16] | len:varint | payload[len]
```

`mseq` присутствует только в *нумерованных* каналах (режимы `unreliable_sequenced` и `reliable_ordered`). `len` может быть 0. Тег не меньше числа настроенных каналов недопустим. Таблица каналов (число и режим каждого, не более 16) это конфигурация, известная обеим сторонам; её хеш проверяется в рукопожатии (раздел 3).

| Режим | Значение | Нумерованный | Гарантия |
|---|---|---|---|
| `unreliable` | 0 | нет | не более одного раза, любой порядок |
| `unreliable_sequenced` | 1 | да | не более одного раза, только новее самого нового из принятых |
| `reliable_ordered` | 2 | да | ровно один раз, по порядку, пока соединение живо |

`mseq` это счётчик на канал и направление, оборачивается на 2^16 и сравнивается как порядковое число (расстояние меньше 2^15).

#### ACK

```
10 | largest:u16 | delay:varint | n:u8 | first:varint | (gap:varint | len:varint) x n
```

- `largest`: младшие 16 бит наибольшего подтверждаемого номера пакета. Получатель кадра восстанавливает его как наибольшее значение, не выше наибольшего отправленного им номера, с этими младшими битами.
- `delay`: как долго отправитель кадра держал пакет `largest` до подтверждения, в единицах по **32 микросекунды**. Нужен для поправки замеров RTT.
- Первый блок подтверждает `first` пакетов, заканчивая `largest`. Каждый из `n` следующих блоков это `gap` неподтверждённых номеров ниже предыдущего блока, затем `len` подтверждённых.
- Ограничения: `n <= 15`, `first >= 1`, `gap >= 1`, `len >= 1`, общий охват `first + sum(gap + len) <= 32768`, и ни один блок не опускается ниже номера пакета 0.

Пакета ack-only не бывает, если подтверждение не должно дольше настроенной максимальной задержки подтверждения.

#### PING

```
11
```

Keep-alive и замер RTT. Требует подтверждения; подтверждение и есть ответ (PONG нет).

#### DISCONNECT

```
12 | reason:u8
```

Мягкое закрытие с однобайтовым кодом причины. Смысл кода принадлежит приложению; ядро определяет только `0` = обычное закрытие. Отправитель шлёт его в трёх датаграммах.

## 3. Датаграммы рукопожатия

Датаграммы рукопожатия открытые. Неиспользованные байты это дополнение и **обязаны быть нулями**.

`HELLO FIELDS` (29 байт), используются в HELLO и RESPONSE:

```
wire_version:u8 | protocol_id:u64 | app_version:u32 | config_hash:u32 | client_random:u64 | caps:u32
```

| Поле | Смысл |
|---|---|
| `wire_version` | `1` для этого документа. При любом другом значении остальные поля не определены, сервер отвечает REJECT. |
| `protocol_id` | ворота приложения на проводе; несовпадение отклоняется |
| `app_version` | версия приложения; совместимость решает приложение |
| `config_hash` | хеш настроек, влияющих на провод (таблица каналов, размер датаграммы); несовпадение отклоняется |
| `client_random` | 8 свежих случайных байт на каждую попытку соединения |
| `caps` | биты возможностей; в v1 не определены, слать 0, неизвестные биты игнорировать |

```
HELLO      80 | HELLO FIELDS | нули до 64 байт
CHALLENGE  81 | coarse:u32 | cookie:u64                                  (13 байт)
RESPONSE   82 | coarse:u32 | cookie:u64 | HELLO FIELDS | нули до 64 байт
ACCEPT     83 | token:u64 | echo:u64 | caps:u32 | blob_len:u8 | blob[blob_len]
REJECT     84 | code:u8 | echo:u64                                       (10 байт)
```

- `coarse`: часы сервера в целых секундах на момент создания куки.
- `cookie`: 64-битная метка, привязанная к адресу (раздел 5). Клиент возвращает `coarse` и `cookie` в RESPONSE вместе с теми же HELLO FIELDS, поэтому сервер ничего не хранит между HELLO и RESPONSE.
- `echo`: `client_random` клиента. Клиент принимает ACCEPT или REJECT, только если `echo` совпадает с отправленным им значением; это мешает атакующему вне пути подделать их.
- `token`: токен сессии (раздел 5).
- `blob`: до 32 байт данных приложения от сервера клиенту (например, параметры игры); `blob_len <= 32`.
- `code` в REJECT: `1` версия, `2` несовпадение настроек, `3` сервер полон, `4` ограничение частоты. Остальные значения определяет приложение.

## 4. Размеры

| Что | Байт |
|---|---|
| Заголовок DATA | 11 |
| Накладные расходы MSG, нумерованный канал, полезная нагрузка до 127 байт | 1 + 2 + 1 = 4 |
| Накладные расходы MSG, ненумерованный канал, полезная нагрузка до 127 байт | 1 + 1 = 2 |
| Кадр ACK, один блок, короткая задержка | около 7 |

Самая короткая DATA 12 байт (PING).

## 5. Выводимые значения (предварительно, этап 2)

- `cookie = SipHash-1-3(ключ = текущий секрет, DOMAIN_COOKIE | addr | coarse | HELLO FIELDS)`, 64 бита. Секрет ротируется, предыдущий тоже принимается. Кука верна, если `coarse` отличается от часов сервера не более чем на 5 секунд.
- `token = SipHash-1-3(ключ = ключ токенов, DOMAIN_TOKEN | addr | client_random | счётчик соединений)`, ключ не совпадает с секретом куки.
- `addr` это непрозрачные байты адреса, которые хозяин передаёт ядру (не более 20 байт).

## 6. Порядок рукопожатия и правила (предварительно, этап 2)

```
клиент                          сервер
  HELLO  ------------------->            ничего не хранит
         <------------------  CHALLENGE   (или REJECT)
  RESPONSE ------------------>            проверяет куку, занимает слот
         <------------------  ACCEPT      (или REJECT)
  DATA ...  <------------->  DATA ...
```

- До верной куки состояния на сервере нет. Лимит частоты действует по источнику и глобально.
- Верный RESPONSE с адреса, у которого уже есть живое соединение: если `client_random` тот же, ACCEPT повторяется (идемпотентно); если другой, старое соединение закрывается и заменяется.
- Таймаут простоя, интервал keep-alive и таймаут рукопожатия это настройки хозяина, а не значения на проводе.

## 7. Версии

`wire_version` (один байт в HELLO) определяет раскладки этого документа. Теги кадров `0x13`-`0x1F`, вид `0x01` и биты `caps` зарезервированы под расширения. Изменение любой раскладки из этого файла требует новой `wire_version`.

## 8. Векторы

`vectors/wire-v1.txt` перечисляет строки байтов и каноничное описание того, как каждую надо прочитать. Формат строки и таблица каналов, которую предполагают векторы, описаны в заголовке файла. Реализация соответствует документу, если для каждой строки печатает ровно перечисленное описание и отбрасывает ровно строки с пометкой `drop`.
