# pkt-voidnet

[English](README.md) · **Русский**

Небольшое самостоятельное сетевое ядро для игр: соединения, режимы доставки, устойчивость к враждебному вводу. Ничего не знает об игре, которая построена на нём.

**Статус: этапы 1-4б готовы: соединения работают и несут данные в симуляторе, есть C ABI и обвязка для Zig, ядро строит датаграмму только по явному `flush` или таймеру (4б).** Формат на проводе, рукопожатие и допуск, доставка (надёжный упорядоченный, ненадёжный, «только свежее») и теперь C ABI (`include/voidnet.h`, память хозяина, без колбэков) и `bindings/zig`. У Tee есть фасад поверх него (`@lib/network/vn` в репозитории Tee, 13 контрактных тестов на Zig 0.17). В игре ещё не пробовали: это этап 5.

## Стек

- Ядро: Rust, по возможности `no_std`, наружу C ABI.
- Первый потребитель: игра Tee на Zig (фасад на Zig поверх ядра).
- Цели дизайна: изоляция, минимальный размер, тестирование без сети (sans-IO), слои, которые подключаются по желанию.

## Команды

```bash
cargo test --workspace                        # юнит-тесты, свойства, имитатор
cargo clippy --workspace --all-targets
zig test vectors/check.zig                    # независимый декодер на Zig против vectors/wire-v1.txt
UPDATE_VECTORS=1 cargo test -p voidnet-core --test vectors   # пересоздать векторы после изменения формата
# библиотека C ABI для Zig под Windows и проверка линковки:
cargo build -p voidnet-ffi --release --features abi --target x86_64-pc-windows-gnu
(cd tests/zig-abi && zig build run -Dtarget=x86_64-windows-gnu)
```

Цели фаззинга: `parse_datagram`, `recv_window`, `ack_frame`, `handshake_flood`, `conn_stream`. Для фаззинга нужен nightly и, на Windows, ASAN-рантайм Visual Studio в `PATH` (см. `spike/RESULT.md`): из `fuzz/` команда `cargo +nightly fuzz run parse_datagram`.

## Как устроено

- `docs/transmit.ru.md`: когда строится датаграмма. `send` только ставит в очередь; датаграмму начинает `flush` или таймер (задержка подтверждения, повтор, проба, keep-alive); подтверждение едет с ближайшей датаграммой и уходит отдельно лишь после `max_ack_delay`. Задержку брать длиннее самого длинного обычного промежутка встречного потока (50 Гц вниз, ввод раз в 50 мс вверх: 60 мс даёт 50 + 20 датаграмм в секунду без отдельных подтверждений; 20 мс даёт лишние 20 в секунду).
- `docs/wire.ru.md`: единственное нормативное описание байтов. `vectors/wire-v1.txt`: строки байтов с каноничным прочтением.
- `crates/voidnet-core`: `no_std`, без выделения памяти, `forbid(unsafe_code)`, индексирование и `unwrap` запрещены линтом. Разбор формата, окно номеров, кадры ACK, соединение (`Conn`: доставка, RTT, потери, таймеры), автоматы `Server` и `Client`. Около 100 КБ на соединение, фиксированно.
- `crates/voidnet-sim`: ГСЧ с зерном, канал с потерями (потери, дубли, перестановка, блэкаут), маленький мир из сервера и клиентов, пара голых соединений, эталонные хеши трасс, сценарии атак, потерь и таймеров.
- `crates/voidnet-ffi`: C ABI (`include/voidnet.h`), `unsafe` живёт только здесь; проверен под Miri. `bindings/zig`: обвязка для Zig и её тесты.
- `crates/voidnet-udp`: ядро на `std::net::UdpSocket` для хозяев на Rust (`UdpServer`, `UdpClient`): сокет, часы, случайные байты, смена секрета, таймеры. `pump(wait)` читает, выполняет таймеры и отправляет; `service()` отправляет готовое сразу после `flush`; `try_clone_socket` + `feed` для хозяина, который ждёт на сокете в своём потоке. Сервер выделяется в куче обнулённым и оживляется через `reset` (единственный `unsafe` крейта). Проверен на loopback под Windows, включая `ConnectionReset` после отправки на закрытый порт.
- Проектирование и обоснования: спецификация сетевого ядра в репозитории Tee (`docs/architecture/netcore-spec.md`).

## Насколько он силён

Замерено на машине автора под Windows, релизная сборка, `opt-level = "z"` (размер, а не скорость), в симуляторе, поэтому цифры включают сам симулятор и всех 64 клиентов и дают пессимистичную оценку для одного ядра:

| | |
|---|---|
| Память | 100 560 байт на соединение, 6,2 МиБ на сервер с 64 клиентами (фиксированно, при работе ничего не выделяется) |
| 64 клиента, 50 Гц в обе стороны, снимки по 400 байт | 17,9 мс процессорного времени на секунду симуляции (около 2% одного ядра) на всю симуляцию; 3 200 датаграмм в секунду на вход, 10,8 Мбит/с на выход |
| Цена одной датаграммы | около 2,8 микросекунды: сервер, клиенты и каналы вместе |
| Поток из 200 000 враждебных датаграмм с 3 000 подменённых адресов | ни одного ответа длиннее запроса, ни одного занятого слота, ни одного события |
| Один адрес молотит рукопожатие | ровно 10 ответов в один момент, дальше его корзина пуста |
| 20 000 подменённых адресов сразу | ровно 500 ответов, дальше останавливает глобальная корзина |
| Надёжный канал, 25% потерь + 10% дублей + 15% перестановки, 30 зёрен | каждое сообщение ровно один раз, по порядку |
| Мёртвый канал | 17 пакетов проб за 10 секунд (удлинение интервалов), сам восстанавливается, когда путь вернулся |
| Одно потерянное сообщение без другого трафика | исправляется за долю секунды, задолго до keep-alive |
| Тесты | 147, плюс 5 целей фаззинга (миллионы запусков, находок в ядре нет), 30 намеренных поломок ядра, все пойманы |

Повторить замер скорости: `cargo test --release -p voidnet-sim --test bench -- --ignored --nocapture`.

Чего в нём **нет**, сознательно: окна перегрузки (он сам не замедляется на забитой линии), шифрования, дробления больших сообщений. Зачем и когда каждое добавлять: `docs/wire.ru.md`, раздел 7, и спецификация.
